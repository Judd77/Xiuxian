# 《问心劫：三十日登仙》完整制作方案

> 开发暂定名。本文整理此前对话确定的整套制作方案，以最新决策为准，不是完成情况报告。
> 版本：1.0。设计基准：1920×1080。目标平台：Windows / Steam。
> 实际进度见 DEVELOPMENT_STATUS.md；下一步见 NEXT_TASKS.md；资源授权见 ASSET_PROVENANCE.md。

## 1. 项目目标与合作方式

制作可完整游玩、可提交 Steam 审核的原创单机修仙游戏，而不是停留在演示。
用户委托助手负责玩法、技术选型、剧情、工程实现、资源制作与开发顺序，尽量直接操作工程，不要求用户反复复制代码。
好玩需要通过试玩证明，不能承诺必然好玩、通过审核或获得销量。完整游戏需要分阶段开发与验证，不能一次工具调用完成。
账号、身份及税务信息、付款、合同、最终发布授权由用户处理；不擅自购买、发布或上传敏感资料。
每阶段记录真实结果，明确区分计划、文件已写入、编译通过、测试通过和实机体验通过。

## 2. 定位与核心体验

类型：修仙悬疑 AVG + 有限日程养成 + 多结局。
核心宣传句：距离宗门献祭还有三十日。你可以拼命修炼成为祭品，也可以查清真相，决定谁能活着登仙。
不是开放世界，不做刷怪 RPG，也不是仅点击下一句的小说。
玩家追求三个互相竞争的目标：获得力量、查明真相、建立可信的关系。
修为最高不等于最好结局；好感最高不代表对方会无条件支持。

## 3. 故事前提与角色范围

主角是刚入宗门的外门弟子，发现三十日后的登仙大典可能以弟子为代价。
三位主要角色分别掌握部分真相，也有各自不能公开的理由。角色动机和完整人物小传仍需正式编写，不假定已有完整剧本。
目前原型使用林月师姐，入门第一日即面临离山调令；旧名册成为调查切入点。
玩家最终可以尝试救人、逃离、夺取仪式或维持它；具体结局条件与道德冲突需在章节设计阶段完善。
重玩价值来自理解不同人物动机与选择后果，不靠反复刷数值或强制多周目解锁唯一真结局。

## 4. 核心日程循环

| 时段 | 设计内容 |
|---|---|
| 晨间 | 剧情事件、人物动向、已知线索与时限提示 |
| 白昼 | 一次主要行动 |
| 傍晚 | 一次主要行动 |
| 夜间 | 关键对话、证据整理、当天结算与后果 |

行动类型：修炼、调查、交往、获取资源。
一天只有两次主要行动；事件随日期和阶段改变，不把同一组按钮重复三十次。
例：师姐今晚离山，而藏经阁禁书今日移交。陪伴师姐会牺牲一次调查机会；先前争取到的盟友可能代查，但信息不一定完整可靠。
重要行动明确显示已知成本与条件，不直接剧透未知结果。
主要判定优先采用确定性条件，减少靠读档刷随机概率。
失败也应带来信息或替代路线，避免只有扣属性。
关键选择在后续有可见回应；不靠无限送礼积累关系。
防止无事件可做的死局，必要时提供基础行动或替代调查路径。

## 5. 首发范围目标

| 项目 | 目标 |
|---|---|
| 平台 | Windows / Steam，离线单人 |
| 语言 | 简体中文首发，文本结构预留本地化 |
| 流程 | 序章、三十日日程、终章 |
| 主要角色 | 3 位 |
| 地点 | 约 6 个，允许昼夜等变体 |
| 结局 | 4 个主要结局及少量失败结局 |
| 单周目 | 目标 3–5 小时，必须以实测修正 |
| 视觉 | 绘卷背景、立绘、少量关键 CG |
| 配音 | 首发不做全语音 |
| 战斗 | 剧情化对抗，不另建大型战斗系统 |

以上全部是范围目标，不是现有内容清单，也不是工期承诺。
暂不制作：开放世界、联机、大型背包、复杂回合战斗、装备强化、炼丹配方、随机地图、宗门经营、庞大技能树。
新增系统必须能强化核心取舍，不能仅因修仙题材就堆功能。

## 6. 养成、关系与证据

### 最小原型
两次行动、修为、林月信任、灵石、旧名册证据与夜间结果。
原型初始数值及行为以 FirstDaySession 的实际代码为准，不套用早期泛用示例数值。
同日行动不能重复领取奖励；读档和重复结算不能额外发放收益。

### 完整版候选属性
境界、修为、心境、悟性、气运、灵石、关系与剧情标记。
是否保留每个属性，要看它能否支持不同决策，不把候选项全部视为必做。
境界先考虑炼气到筑基，不一开始制作几十级突破系统。
角色关系可包括信任、是否认识、路线状态、事件解锁；好感与信任是否拆分由玩法验证决定。
证据要可回看、可关联事件，关键选项可以要求特定证据或关系。
条件示例：理解剑诀需要悟性、抵抗心魔需要心境、进入禁地需要令牌、合作需要先前承诺。

## 7. 剧情与演出系统

代码负责执行，剧情数据负责描述，避免正式剧本大量写死在 C#。
技术选择：轻量 JSON 剧情节点，不同时引入 Ink 和 Yarn，不开发庞大可视化编辑器。
最小指令集合：对话、选项、条件、变量与标记变化、背景切换、立绘与表情、音效与音乐、节点跳转、日程推进。
数据使用稳定 ID；校验重复 ID、缺失目标、缺失资源及可检测的不可达节点。
演出功能按优先级加入：点击推进、打字机与补全文字、选项、立绘高亮、淡入淡出、对话历史、自动播放、仅已读快进。
目前线性开场 JSON 只是起点，不等于完整节点播放器已完成。

## 8. 第一阶段：第一日《山门夜雨》

目标完整切片时长约15–20分钟，需要扩写并计时；当前规则演示只有几分钟。
流程：入宗认识师姐 → 得知登仙资格 → 发现失踪弟子线索 → 两次主要行动 → 夜间对质/事件 → 不同后续。
当前原型结果名：雨夜同谋、孤证、门外剑声、不安之夜。这些是第一日结果，不是全游戏四大结局已经完成。
切片需要覆盖对话、时间成本、证据、关系、修为、至少两种显著差异结果和存取档。
先用占位资源跑通，再制作一组正式资源确定画面基准。

### 切片验收
- 从标题到第一日结束无需改代码。
- 行动产生清晰代价，不存在全拿的隐性默认路线。
- 不同选择确实改变后续，而不只是结算数字不同。
- 保存读取不会重复奖励、漏事件或丢失位置。
- 不出现无按钮、日期不能推进的死局。
- 玩家能说出选择理由，不只比较哪个选项加数值最多。
- 切片不好玩则修正，不直接复制扩写成三十日。

## 9. 技术栈与职责划分

| 领域 | 决策 |
|---|---|
| 引擎 | 当前 Unity 6000.6.2f1，URP |
| 语言 | C# 9 |
| UI | UGUI + TextMeshPro（正式方案） |
| 输入 | Unity Input System，先鼠标与键盘 |
| 数据 | JSON 剧情、独立 C# 游戏状态 |
| 演出 | 图片分层、CanvasGroup、轻量动画 |
| 存档 | 版本化 JSON，临时文件、备份、损坏处理 |
| 测试 | Unity Test Framework、规则测试、剧情校验、运行验证 |
| 版本管理 | Git；大资源按需 Git LFS，先核查仓库状态 |
| Steam | 核心流程稳定后再接入，离线可玩优先 |

模块职责：游戏流程协调、剧情执行、背景与立绘展示、音频、日程、修仙数据、关系、证据、存档和 UI。
管理器只负责协调，不把全部功能塞进一个 GameManager。
状态与界面对象分离，避免把 GameObject 引用序列化成存档。
当前 FirstDayPrototype 是临时整合脚本，后续应拆分展示、存档与剧情职责，不视为最终架构。

## 10. 工程目录与场景

游戏内容集中在 Assets/_WenXinJie/，文档放根目录 Docs/。
建议逐步形成 Art/Backgrounds、Art/Characters、Art/CG、Art/UI、Audio/BGM、Audio/SFX、Audio/Voice、Data、Fonts、Materials、Prefabs、Scenes、Scripts、Editor、Tests。
不要求一次创建所有空文件夹。保留原 Settings、Welcome、SampleScene 和未知用户文件。
目前独立原型场景为 Assets/_WenXinJie/Scenes/Prototype.unity。
正式场景规划：MainMenu、Game；需要统一初始化时再加入 Bootstrap。
AVG地点通常通过更换背景实现，不为每个地点单独创建 Unity 场景。

界面分层：背景 → 立绘 → 演出效果 → 对话与选项 → 状态 → 弹窗。全屏淡出遮罩根据需求置顶。
核心窗口：标题、对话、行动选择、状态与证据、历史、存档/读取、设置。

## 11. 分辨率、文字与适配

设计基准统一1920×1080，16:9。不是强制所有玩家使用该窗口分辨率。
当前原型使用 CanvasScaler 的 Scale With Screen Size / Expand，设计框居中；其他宽高比必须测试，不能只靠设置推断适配通过。
正式图片按1920×1080或更高制作，文字与按钮由UI排版，不将主要中文按钮文字烘焙在背景图里。
最终验证1080p、720p、16:10、超宽屏以及窗口缩放；检查遮挡、裁切、可读性、按钮命中和安全边距。
中文字体必须取得清楚授权，验证标点、省略号、破折号、数字以及角色/功法生僻字。
当前暂用UGUI Text动态访问本机中文字体做本地试玩，未复制系统字体文件；不可据此宣称可跨机器发行。后续迁移授权字体与TMP。

## 12. 美术方向与制作顺序

方向：低饱和青绿山水、旧纸纹理、朱砂强调；人物偏东方绘本，不追求写实摄影。
顺序：占位原型 → 一张正式背景、一位角色、一套对话UI → 第一日完整资源 → 扩展全游戏。
先建立角色基准设计，再做表情和CG，核查服饰、比例、发饰、配色和身份一致性。
立绘使用透明背景，同角色表情保持画布、锚点和站位一致，避免切换跳动。
背景16:9；不需要透明通道的背景可用适当压缩格式；CG单独管理。
命名保持角色/场景/表情/版本可追踪，不用大量不明含义的final文件。
生成图仍需透明边缘、裁切、压缩、Sprite导入、UI引用和实机场景检查，不把概念图直接视为合格成品。
素材制作工具按当时实际可用模型选择，不保证每个模型可用或免费。

## 13. 音频与资源采购

先用临时声音验证流程；正式制作背景音乐、环境声、按钮提示和关键事件音效。
首发不做全语音，避免放大制作与迭代成本。
可在Unity生成接口查询当前可用音频模型后选用；有接口不意味着已确认可生成、授权或费用。
如使用外部资源，必须明确商业许可、署名和再分发条件；免费不等于可商用。
正式配乐和图片需要一致风格，音量与循环接缝须实测。
首次Unity资源生成前列出具体资源并取得确认：任务可能并行，但调用等待时助手不能执行其他工作或中途回复；几十秒到数分钟且无精确ETA。
付费、订阅、登录协议等额外征得用户许可。不要在公共服务中上传密钥或私人工程数据。

## 14. 存档与设置

需要保存剧情位置、日程与行动次数、角色属性、关系、证据、标记、背景/音乐状态（具备对应演出后）。
已读记录、CG解锁等全局进度和单个周目存档分开设计；设置独立保存。
阶段顺序：单槽可验证 → 备份与恢复 → 多槽与自动存档 → 版本迁移、截图和展示信息。
验证覆盖重复奖励、缺失/损坏文件、不支持版本、非法状态、旧档恢复、读写失败提示。
测试使用独立临时路径，不能覆盖用户试玩存档。
设置至少包括主音量/音乐/音效、文字速度、自动播放间隔、窗口/全屏及必要的可读性选项。

## 15. 开发里程碑与验收

### M0 工具与可续接工程
验证Unity连接、文件写入、编译、Console；建立交接文档和修改保护。
### M1 最小闭环
标题、开场、两次行动、分支结果、重玩、存档；规则与运行测试。
### M2 第一日正式切片
剧情节点化、角色动机、选择反馈、授权字体、基本演出、统一正式视觉、音效和历史；试玩迭代。
### M3 三十日完整骨架
阶段日程、地点解锁、角色事件、证据和关系路线、终章；先保证全流程可达和无死局。
### M4 内容与体验完善
完整剧情、美术与音乐、重要CG、自动/已读快进、设置、多槽存档、适配与性能。
### M5 发行候选
Windows构建、干净环境安装测试、版本兼容、授权与AI披露检查、Steam商店资产与审核。
每个阶段经过验收才扩大范围；没有确定日历工期，不以代码量替代可玩性。

## 16. 好玩与质量验证

邀请未参与制作的人试玩，记录：首次理解规则用时、选项理由、困惑点、放弃点、是否想重玩、是否能解释选择后果。
检查是否存在显然最优且长期无代价的路线；若有，调整事件机会成本，而不是简单把数值砍低。
重要代价须能提前形成合理预期，避免结局突然惩罚玩家此前无法判断的信息。
测试维度分开：纯规则、剧情数据、UI按钮事件、实际鼠标射线、视觉截图、实机流程、磁盘存档、发行构建。
按钮事件测试不等于真实鼠标点击测试；编译成功不等于游戏质量达标。
输出验证日志并更新进度，不能隐去失败或把未完成的验证写成通过。

## 17. Steam发行准备

游戏：离线启动、完整流程、多结局、存档、设置、窗口适配、异常恢复与清晰退出。
交付物：Windows构建、版本号、说明与支持渠道；目标机器运行测试。
商店：介绍文案、准确功能描述、胶囊图、真实截图、实机预告片、语言与配置要求。
合规：素材/字体/音频授权、AI使用记录及按当时Steamworks要求披露、适当内容评级和警示。
商业定名前核查商标与同名；不提前承诺售价、销量、审核通过日期。
用户处理开发者账号、付款、身份/税务和协议；构建上传与公开发布必须明确授权。
Steam当前政策、费用、时间要求均在发行前查官方资料；此前网络搜索失败，未完成最新政策核实。

## 18. 风险与控制

范围膨胀：坚持首发边界，新增系统先证明对核心体验有益。
文本过长但选择无意义：先测第一日的决策，再扩写。
生成资源不一致：角色设计基准、少量试产、统一风格检查。
缺字/授权：尽早验证正式字体，记录许可证，不分发来源不明资源。
存档破坏：稳定ID、版本字段、校验、备份与独立测试。
依赖/联网问题：离线可玩，必要才加包，保留现有能用的工具。
上下文丢失：每阶段写入Docs，新会话主动读文档，不依赖聊天记忆。
